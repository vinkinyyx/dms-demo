### 9.1 为什么首轮测试会浮于表面——根因分析

#### 9.1.1 四大测试盲区

| 盲区类型 | 具体表现 | 导致遗漏的Bug | 严重程度 |
|---------|---------|-------------|---------|
| **入口盲区** | 只验证"页面能不能打开"，不验证"顶部按钮全不全" | 销售/采购订单无新增按钮、报台无查看按钮 | 🔴高 |
| **详情盲区** | 详情弹窗能打开就当通过，不检查弹窗里是否有核心业务内容（产品明细） | 订单详情无产品明细 | 🔴高 |
| **交互盲区** | 看到表单字段就OK，不区分"应该手填"还是"应该选择" | 报台批次/序列号手填 | 🟡中 |
| **数据盲区** | 无数据模块直接跳过，不造数据验证详情和流程 | 销退/采退/库存调整详情完全没测 | 🟡中 |

#### 9.1.2 改进方案：五层验证模型

以后每个模块必须走完5层，第5层过不了不算"通过"：

```
L1 入口层 ── 顶部按钮/操作列按钮/菜单项，对着需求清单逐项打勾
  ↓
L2 列表层 ── 字段完整性/筛选/排序/分页，列字段对照表核对
  ↓
L3 详情层 ── 三要素：基本信息 + 业务明细 + 操作/审批记录，缺一不可
  ↓
L4 交互层 ── 每个可编辑字段问：数据源在哪？应该手填还是选择？校验规则？
  ↓
```

### 9.7 测试方法论改进措施

| 保证措施 | 具体做法 |
|---------|---------|
| **入口必查** | 每个列表页第一件事：数顶部按钮数，对照需求文档打勾，少一个都不行 |
| **详情三要素** | 详情弹窗/页面必须包含：基本信息区 + 业务明细表 + 操作/审批记录区，三者缺一不可 |
| **字段溯源法** | 对每个可编辑字段，问三个问题：数据源在哪？应该手填还是选择？有什么校验规则？ |
| **API对比法** | 前端UI验证完后，调一次详情API，对比后端返回了多少字段、前端展示了多少字段，差距大就是问题 |
| **无数据必造** | 任何模块不能因为"列表为空"就跳过，必须通过API或手工造数据，至少验证1条完整流程 |
| **全链路验证** | 不验证单个页面，验证完整链路：创建→审批→执行→库存变化→报表体现 |

#### 9.9.5 技术发现与约束

1. **分页参数约定**：后端统一使用 `size`（而非 `pageSize`），页参数为 `page`
2. **业务成功码约定**：`code = 0` 表示成功（HTTP 200 + code 0 双重验证）
3. **响应结构**：统一为 `{code, message, data}`，列表数据在 `data.items` 中，total在 `data.total`
4. **Token隔离**：业务前台Token（/api/auth/login）与平台后台Token（/api/admin/auth/login）严格分离
5. **ApiClient封装**：统一提供 `is_success` / `assert_success` / `items` / `body` 等便捷属性
