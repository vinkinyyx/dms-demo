# 第一篇：功能缺口与优化需求评估

## 0. 评估方法与分级说明

### 0.1 优先级 (P)
- `P0`：阻塞核心业务/演示/合规，必须尽快做
- `P1`：影响主要使用者日常效率或体验，建议下一迭代
- `P2`：增强/完善类，可排期
- `P3`：远期/锦上添花

### 0.2 工作量 (人·日)
以一名熟悉项目的全栈工程师为基准，含前后端联调与基本自测，不含全量回归与发布。

### 0.3 实现难度
`低 / 中 / 中高 / 高`（高 = 涉及工作流、架构、多端联动、历史数据迁移或外部系统集成）

### 0.4 模块标签
`MOB` 移动端 / `LOG` 日志审计 / `APV` 审批流 / `BIZ` 核心业务 / `PC` 业务前台 / `ADM` 平台后台 / `NF` 非功能性 / `UI` UI/UX / `INT` 对外集成 / `SEC` 安全 / `DAT` 数据与报表 / `QA` 测试质量 / `OPS` 运营配置 / `UX` 用户体验 / `GOV` 数据治理 / `DR` 容灾连续性 / `MAINT` 可维护性 / `COMP` 合规

### 0.5 现状态标记
- `[已实现]` 浏览器实际验证可访问且功能正常
- `[部分实现]` 有页面或后端但功能不完整
- `[未实现]` 完全缺失
- `[已上线]` 文档明确标注已上线
- `[规划中]` 仅 PRD 提到未开发
- `[缺陷]` 已实现但有 bug

### 0.6 本次评估新增方法
相比 v3.12 版本，本次评估新增：
1. **三端实际点击验证**：业务前台 47 页、平台后台 24 项、移动端 8 页 100% 覆盖
2. **需求文档全量比对**：覆盖 11 份核心需求文档共 3000+ 条需求点
3. **需求遗漏识别**：识别出 23 项需求文档未明确但业务必需的功能
4. **新增需求建议**：基于行业最佳实践提出 45 项新需求建议（含 v3.12.2 补充的 UI 设计系统、前端性能、后端架构、可观测性、容灾、安全合规、数据治理、可维护性、API 治理、用户体验深化 10 大维度 27 项）

## 2. 移动端需求详细描述（MOB）

### MOB-01 手术报台拍照与扫码录入 `[P0, 4-6 人日, 中]` `[未实现]`

**现状（2026-08-12 验证）**：
- `MSurgeryReportCreate.vue` 中产品通过搜索选择，批号/序列号靠手输
- `surgery_reports` 表预留了 `attachment_file_id/attachment_name/attachment_url` 字段，但前端未提供上传入口
- 浏览器验证：报台创建页 `input[type=file]=0`、`van-uploader=0`、扫码相关关键词 count=0
- 浏览器验证：报台创建页**没有"批号"、"序列号"输入框**，仅产品选择器

**需求详细描述**：
1. **扫码录入**：H5 端调用相机扫描条码/UDI/序列号，自动带出产品、批号、序列号；相机不可用时降级为手输
2. **拍照上传**：报台时对手术现场、产品标签、植入卡片等拍照，多图上传 MinIO，写入 `attachment_*` 字段
3. **UDI 码自动解析**（GS1 标准）：批号、序列号、生产日期、有效期自动回填
4. **报台详情页支持图片预览**、放大、删除（草稿期）
5. **产品行支持批号/序列号字段**：按产品 `is_serial_managed` 自动切换显示批号或序列号输入框
6. **数量字段必填且 > 0**

**价值**：现场销售/跟台最核心的移动场景，避免手输错误，方便术后追溯

**依赖**：MinIO 已有；前端可用 `@zxing/browser` 或 `html5-qrcode`；UDI 解析新增工具类

**风险**：移动端浏览器相机权限、UDI 码制差异（GS1-128 / DataMatrix / QR）

# 第二篇：需求优先级排序与开发建议

## 一、核心结论（先看这段）

1. **重写版文档很全面，但存在"把已有功能当未实现"的误判**。浏览器验证时因登录角色权限不足，把销售订单、销售出库、库存移动、经销商管理、账号管理、销售岗位、审批中心、接口/邮件日志、经销商画像、产品对码等**已实现页面**标成了"未实现"（代码中 `modules.js` + 路由均存在，只是菜单/权限未对当前角色显示）。因此 BIZ-11～BIZ-18 的"页面迁移"工作**大部分不需要做**，应改为"权限与菜单核对 + 缺陷修复"。
2. **真正的 P0 只有三类**：移动端核心闭环（报台扫码拍照、移动审批、移动消息）、审批内容可视化、日志/安全合规的基础项（登录日志页、密钥外置、越权回归）、以及几个 0.5 人日的小缺陷。原文档把约 30 项都标成 P0，稀释了重点。
3. **大量"架构级"需求（读写分离、MQ、分布式追踪、API 网关、K8s、单元测试 80% 覆盖、设计系统全面重构、等保全套）在当前阶段不值得做**。当前是单租户/少量租户的演示+早期交付阶段，这些会拖慢交付且没有真实流量/合规压力，应降到 P2/P3 或在真实需要时再做。
4. **UI 设计系统（NEW-19～27）方向正确，但不应作为大项目一次性投入**。建议：先做"状态规范统一 + 响应式 1366 适配 + 主色/间距 Token 最小集"，不要现在就做全组件库重构、暗色模式、动效体系。
5. **建议按三个迭代推进**，每个迭代控制在 20-30 人日（约 3-4 周一迭代，1-2 名全栈），优先交付可见、可演示、可验证业务价值的功能。

## 四、对原文档方法论的几点提醒

1. **"三端实际点击验证"存在假阴性**。用无权限角色登录看到 404/菜单隐藏 ≠ 功能未实现。建议复核时用 `sys_admin/Sh123456`（或具有全权限的账号）登录后再判断。本文已根据代码修正 BIZ-11～BIZ-18 的误判。
2. **"行业最佳实践"不等于"当前要做"**。NEW 系列很多是大厂/成熟期架构（读写分离、MQ、追踪、网关、MDM），套在当前一个单库、几十用户的系统上会严重过度设计，反而增加运维负担和交付风险。
3. **P0 必须收敛**。原文档 P0 有 30+ 项，已经失去优先级意义。建议 P0 控制在 10 项以内，且必须是"不做就不能演示/不能交付/有合规风险"。
4. **UI/UX 投入要适度**。设计系统方向对，但不要在没有专职设计师的情况下让工程师花 5-8 天去做 Token 体系和组件库；做最小集（主色、间距、状态规范、1366 适配）性价比最高。
5. **先做能演示的功能，再做架构**。当前阶段，移动端扫码报台、移动审批、审批摘要对销售演示和成单的价值，远大于引入 MQ/追踪/读写分离。
