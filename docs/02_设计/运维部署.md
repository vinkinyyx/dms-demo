## DMS 服务器迁移/复刻清单

### 1. 新服务器准备

- 准备 Linux 服务器，建议 Ubuntu 22.04+，磁盘不少于 40 GB，内存不少于 2 GB。
- 安装 Docker 和 Docker Compose 插件，启动 Docker 并设置开机自启：
  - `systemctl enable --now docker`
- 开放端口：
  - 生产前端：`8081`
  - 生产后端：`8080`
  - 测试前端：`8083`
  - 测试后端：`8082`
  - PostgreSQL：`5432`、`5433`
  - Redis：`6379`、`6380`
  - MinIO：`9000`、`9001`、`9002`、`9003`
  - Mock：`9090`
  - 宣传页：`8084`
  - 如经 Nginx 统一入口访问，再开放 `80`。
- 创建部署目录：`/opt/dms`。

### 2. 迁移代码和静态文件

- 复制以下目录到新服务器：
  - `/opt/dms/frontend-vue`
  - `/opt/dms/dms-test/frontend-dist`
  - `/opt/dms/dms-test/admin-dist`
  - `/opt/dms/brochure`
  - `/opt/dms/mocks`
  - `/opt/dms/scripts`
  - `/opt/dms/docker-compose.yml`
  - `/opt/dms/docker-compose.test.yml`
- 检查前端、Nginx、后端配置中的 IP、域名、端口、API 地址，替换为新服务器地址。
- 确认生产前端容器使用的是当前 `dist` 内容，测试前端容器使用的是当前 `frontend-dist/dist` 和 `admin-dist` 内容。

### 3. 迁移数据库和对象存储

- 迁移生产 PostgreSQL：
  - 源容器：`dms-postgres`
  - 数据库：`dms`
  - 用户：`dms`
  - 数据卷：当前生产库挂载的 Docker volume
- 迁移测试 PostgreSQL：
  - 源容器：`dms-test-postgres`
  - 数据库：`dms_test`
  - 用户：`dms`
  - 端口：`5433`
- 迁移 Redis：
  - 生产容器：`dms-redis`
  - 测试容器：`dms-test-redis`
- 迁移 MinIO：
  - 生产容器：`dms-minio`
  - 测试容器：`dms-test-minio`
  - 同步 bucket、access key、secret key 和持久化卷数据。
- 迁移方式二选一：
  - 冷迁移：停源库后用 `pg_dump`/`pg_restore` 导出导入，并复制 Redis/MinIO volume。
  - 卷迁移：停止新旧容器后直接复制 Docker volume 数据目录。
- 迁移后校验：表数量、租户、用户、基础数据、附件文件、业务数据条数。

### 4. 迁移或重建镜像

- 可直接导出导入现有镜像：
  - `dms-backend:latest`
  - `dms-backend-test:latest`
  - `dms-frontend-vue:latest`

  - 后端：使用 `backend/Dockerfile.aliyun` 或服务器实际 Dockerfile 构建。

  - `postgres:14-alpine`

  - `nginx:1.25-alpine`
  - `minio/minio:latest`
  - `wiremock/wiremock:3.3.1`

### 5. 启动容器

- 创建 Docker 网络：`dms-net`。
- 按依赖顺序启动：
  - PostgreSQL、Redis、MinIO
  - 后端
  - 前端/Nginx
  - Mock、宣传页等辅助服务

  - `--restart unless-stopped`
- Docker 服务设置开机自启：
  - `systemctl enable docker`

- Redis 地址、端口、密码。

  - 生产前端：`http://新服务器IP:8081/`

- 保留旧服务器和旧镜像，至少保留一个回滚窗口。
- 回退方式：将流量切回旧服务器，并恢复迁移期间新增数据。

#### A.2 前端产物替换流程

1. 本地在 `frontend-vue/` 执行 `npm run build`，确认 `dist/` 包含最新 PC 与移动端资源。
2. 打包 `dist/` 为 zip，上传到服务器临时目录。
3. 替换前先备份旧产物，例如：`cp -a dist dist.bak.$(date +%Y%m%d-%H%M%S)`。
4. 使用清空目录后解压的方式替换，避免旧 hash chunk 残留。
5. `docker restart dms-test-frontend` 或 `docker restart dms-frontend-vue`。
6. 验证：首页、登录、关键 API、移动端路由（如 `/mobile/home`、`/mobile/dashboard`）、`/assets/*.js` chunk 均返回 200。

#### A.3 回滚要点

- 测试前端：从 `dist.bak.<timestamp>` 恢复后重启 `dms-test-frontend`。
- 生产前端：保留上一版本镜像 tag，例如 `dms-frontend-vue:backup-<timestamp>`，回滚时停止当前容器并用旧镜像重新启动。
- 后端：至少保留上一版本可运行 jar 或镜像；回滚后检查 Flyway 版本、健康检查和核心接口。

#### A.4 Docker Compose / Seed 历史说明

- 基础服务包括 PostgreSQL、Redis、MinIO、Nginx、后端、前端、Mock 服务。
- 首次启动通过 Flyway 自动迁移，Seed 数据用于演示和测试。
- 演示账号以最新 `docs/DMS登录信息手册.md` 为准，历史文档中出现的 `admin / Sh123456`、`D00001_01 / Sh123456` 可能因首次登录强制改密或租户隔离而变化。

#### A.6 常见故障快速处理

- 端口冲突：更换宿主机映射端口或停止占用进程。
- 镜像构建失败：先执行 `df -h /` 检查磁盘，再执行 `docker system prune -af` 清理缓存。
- 页面无法访问：检查容器状态、防火墙/安全组、Nginx 代理目标和后端健康检查。
- API 401/403：确认登录环境、租户类型、token 和 Nginx 是否放行对应 `/api/` 路径。

## 四、生产环境服务器配置建议（中小型企业）

> 评估日期：2026-08-14
> 适用场景：单租户或少量租户的中小型医疗器械/耗材经销企业，DMS 全栈（Spring Boot 后端 + Vue 前端 + PostgreSQL + Redis + MinIO + Nginx）以 Docker Compose 部署。

### 1. 业务量与容量假设

| 指标 | 取值 | 说明 |
|---|---|---|
| 年销售额 | 2–5 亿元 | 客单价按医疗器械耗材估算 |
| 日均订单量 | ≈100 单/天（销售订单+采购订单合计） | 业务高峰集中在工作日白天 |
| 单据放大系数 | 每单约 3–5 条明细、1–3 次收发执行 | 含订单行、出入库子单、库存流水 |
| 年新增业务数据行 | 约 50–100 万行 | 订单/明细/库存事务/日志合计 |
| 并发用户数 | 20–50 个注册用户，峰值在线 10–20，并发请求 5–15 | 销售/采购/仓库/财务/管理多角色 |
| 数据保留 | 业务数据长期保留，日志/报文按策略清理 | 库存流水不可篡改，至少保留 3–5 年 |
| 附件体量 | 合同/资质/报台照片/接口报文，年均 5–20GB | 取决于拍照与附件上传频率 |

**结论**：该量级属于轻量 OLTP 负载，数据库规模 3 年内约 5–15GB（含索引，不含附件），**单台中等规格云服务器即可稳定承载**，无需上集群或分布式；预算允许时建议数据库与应用分离以提升稳定性与可维护性。

### 2. 推荐配置方案（三选一）

#### 方案 A：单机一体化部署（性价比首选，推荐起步）

全部容器部署在同一台云服务器，适合用户数 ≤50、无强高可用要求的中小企业。

| 资源 | 推荐规格 | 说明 |
|---|---|---|
| CPU | **8 vCPU**（x86，如 Intel Xeon / AMD EPYC 2.5GHz+） | 后端 + Nginx + DB + Redis 共用，报表/导出时有峰值 |
| 内存 | **16 GB** | JVM 4G、PostgreSQL shared_buffers 4G、Redis 512M–1G、MinIO+系统余量 |
| 系统盘 | **100 GB SSD** | OS、Docker 镜像、应用 jar/前端 dist |
| 数据盘 | **200–500 GB SSD（单独挂载）** | 数据库数据、MinIO 对象、备份；建议独立数据盘便于快照与扩容 |
| 带宽 | **5–10 Mbps 固定带宽**（或按流量计费） | 日常 100 单文本为主；附件上传/导出多时建议 10M |
| 操作系统 | Ubuntu 22.04 LTS | 与测试环境一致 |
| 部署 | Docker + Docker Compose | 沿用现有 `/opt/dms/prod` 目录结构 |

**JVM 参数建议（容器内）**：
`-Xms3g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -Duser.timezone=Asia/Shanghai`

**PostgreSQL 关键参数（16GB 内存参考）**：
```ini
shared_buffers = 4GB
effective_cache_size = 12GB
work_mem = 32MB
maintenance_work_mem = 512MB
max_connections = 100
wal_buffers = 16MB
checkpoint_completion_target = 0.9
random_page_cost = 1.1          # SSD
log_min_duration_statement = 500  # 记录慢 SQL
```

**各容器内存分配参考**：后端 JVM 4G、PostgreSQL 5G（含缓存）、Redis 1G、MinIO 1G、Nginx 256M，剩余留作系统与构建/导出缓存。

#### 方案 B：应用与数据库分离（稳定性更好，推荐 1–2 年内演进）

应用服务器与数据库服务器分离，可独立扩容、独立备份，数据库可使用云 RDS 降低运维成本。

| 角色 | 规格 | 部署内容 |
|---|---|---|
| 应用服务器 | **4 vCPU / 8 GB / 100GB SSD** | 后端、Nginx、Redis、MinIO |
| 数据库服务器 / RDS | **4 vCPU / 8–16 GB / 100–200GB SSD（高可用云盘）** | PostgreSQL 16，建议开启自动备份与慢日志 |
| 对象存储（可选） | 云 OSS/COS | 附件量大时将 MinIO 迁移到云对象存储 |
| 带宽 | 5–10 Mbps | 同上 |

> 说明：Redis 在 DMS 中主要承担缓存与会话，数据量小，与应用同机即可；生产建议开启 Redis AOF 持久化或接受重启后缓存重建。

#### 方案 C：最小可用配置（预算受限 / 用户极少）

仅适合 ≤10 个用户、数据量小、可接受偶发重启的场景（不推荐作为正式生产长期方案）。

| 资源 | 规格 |
|---|---|
| CPU | 4 vCPU |
| 内存 | 8 GB |
| 磁盘 | 100 GB SSD（系统+数据） |
| JVM | `-Xms1g -Xmx2g` |
| PostgreSQL shared_buffers | 2GB |

### 3. 存储与容量规划

| 数据类型 | 3 年预估体量 | 建议 |
|---|---|---|
| PostgreSQL 业务数据 | 5–15 GB | 独立数据盘，开启每日逻辑备份 + 定期快照 |
| MinIO 附件/报文 | 15–60 GB | 合同、报台照片、接口原始报文；建议数据盘 ≥200GB 或迁移云 OSS |
| 日志（journal/容器/Nginx） | 每节点 5–10 GB | journal 保留 14–30 天，Nginx 日志 logrotate 按天切割保留 30 天 |
| 备份空间 | 数据量的 1.5–2 倍 | 本地保留最近 7 天，异地/对象存储保留最近 30 天 |

> 建议数据盘初始 200GB 起步，云盘支持在线扩容；按年增长 20–30% 预估，3 年内无需频繁扩容。

### 4. 网络与安全

1. **仅对公网暴露 80/443/22**；PostgreSQL(5432)、Redis(6379)、MinIO(9000)、后端(8080) 一律仅监听 Docker 内网，禁止公网开放。
2. **生产强制 HTTPS**：用 Nginx + Let's Encrypt（或公司证书）配置 TLS，80 强制跳转 443。
3. SSH：禁用密码登录、改用密钥；修改默认端口、限制来源 IP。
4. 安全组/防火墙遵循最小权限原则；数据库与应用若分离，DB 安全组仅允许应用服务器内网 IP 访问。
5. 所有中间件与初始账号密码必须在部署时替换为强密码（PostgreSQL、Redis、MinIO、平台/租户管理员），禁止使用测试环境默认密码。

### 5. 备份与容灾（生产强制要求）

| 项目 | 策略 |
|---|---|
| 数据库逻辑备份 | 每日凌晨 `pg_dump` 全量，保留 7 天；备份文件 gzip 压缩后上传异地/对象存储 |
| 数据库快照 | 若使用云盘/RDS，开启每日自动快照，保留 7–14 天 |
| MinIO/附件备份 | 每周增量同步到对象存储或备份机；重要合同/资质附件跨可用区冗余 |
| 配置备份 | `docker-compose.yml`、`.env`、Nginx 配置纳入 Git 私有仓库（密钥除外，使用环境变量/密钥管理） |
| 恢复演练 | 每季度做一次恢复演练，验证备份可用；明确 RPO ≤ 24h、RTO ≤ 4h |
| 上线前 | 完成一次全量备份与一次"备份→新环境恢复→验证登录与核心流程"的闭环 |

### 6. 监控、告警与运维

1. 开启 Spring Boot Actuator 健康检查（`/actuator/health`），配合简单探活脚本或云监控。
2. 监控指标：CPU、内存、磁盘使用率（≥80% 告警）、容器状态、PostgreSQL 连接数与慢查询、Redis 内存、Nginx 5xx 比例。
3. 日志：容器日志按大小+天数轮转（`max-size=100m, max-file=7`）；journal 保留 14–30 天；接口原始报文按文档策略保留 90 天。
4. 部署：测试环境验证通过后再发布生产，采用"替换 jar/前端 → 滚动重启后端 → 冒烟验证"流程；保留上一版本 jar 作为快速回滚。
5. 生产、测试环境物理隔离，使用独立数据库、独立对象存储桶、独立域名与证书。

### 7. 云厂商选型参考（2026 年华东区大致水平）

| 方案 | 典型规格 | 适用 |
|---|---|---|
| 阿里云/腾讯云/华为云 通用型 g7/c7 | 8 vCPU / 16 GB / 200GB SSD / 5M | 方案 A，单机一体化 |
| 云 RDS PostgreSQL（高可用版） | 4 vCPU / 8 GB / 100GB | 方案 B，数据库托管 |
| 对象存储 OSS/COS | 标准存储 + 低频归档 | 附件与备份 |

> 以上配置为建议起点。实际选型时，若报表查询频繁、导出量大、并发用户接近 50，可优先把内存提升至 32GB 或采用方案 B；若未来扩展到多租户大客量（日均单量 >500、用户 >200），再考虑读写分离、应用多实例 + 负载均衡、对象存储外置与消息队列。
