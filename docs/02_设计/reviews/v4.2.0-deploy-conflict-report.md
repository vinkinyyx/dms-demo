## 2. Flyway 迁移冲突核查（需部署密码执行）

### 2.1 新增迁移
- `V110__fix_schema_drift_email_logs_price_scope.sql`
  - `email_logs.duration_ms` INT → BIGINT（对齐实体 Long）
  - `product_prices.price_scope` 默认值改为 'SALE'
- `V111__fix_period_yyyymm_varchar.sql`
  - stocktakes / rebate_previews / rebate_settlements / dealer_kpi_snapshots 的 `period_yyyymm` CHAR(6) → VARCHAR(6)
- `V112__normalize_price_scope_legacy.sql`
  - 归一化 product_prices.price_scope 历史脏值（'SALES'/'GLOBAL' 等 → 'SALE'/'PURCHASE'），带价格非零条件

### 2.2 安全性分析
三条迁移均为**幂等**操作：
- PostgreSQL 中 `ALTER COLUMN ... TYPE BIGINT/VARCHAR` 在列已是目标类型时不报错；
- `ALTER COLUMN ... SET DEFAULT` 重复执行无副作用；
- V112 是带 WHERE 条件的 UPDATE，重复执行只影响仍是脏值的行。
因此即使目标库 schema 已经漂移到目标形态，迁移语句本身也不会失败。

### 2.3 残留风险
唯一风险：测试库 `flyway_schema_history` 中**已存在 version=110/111/112 的记录**（例如之前用不同 SQL 内容跑过），此时 Flyway 启动会以 checksum 不一致报错并阻止启动。
由于这些迁移文件在当前 working tree 中是未跟踪新文件（HEAD f666ccb 不含），按提交历史推断测试库不应有记录，但**必须在部署前用下面命令确认**。

### 2.4 部署前必跑命令（拿到 DMS_DEPLOY_PASSWORD 后）
```bash
ssh ubuntu@43.128.145.141
sudo docker exec dms-test-postgres psql -U dms -d dms_test -c \
  "SELECT version, description, success, installed_on FROM flyway_schema_history WHERE version IN ('110','111','112') ORDER BY installed_rank;"
```
- 若返回 **0 行**：无冲突，直接部署，V110-V112 会自动应用。
- 若返回记录且 success=true：比对 checksum；若与本次产物不一致，执行 `flyway repair` 或在确认迁移语义一致后用 `flyway repair` 更新 checksum，再部署。
- 若有 success=false 的失败记录：需先人工处理（清理失败记录 + 确认 schema 状态）。
