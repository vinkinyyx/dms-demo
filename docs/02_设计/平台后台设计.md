## 一、架构与多租户隔离设计


﻿# 架构与多租户隔离设计

**版本**：v1.0  
**日期**：2026-08-02

---

### 1. 目标

采用“平台运营方 → 厂家租户 → 经销商租户”的三层 SaaS 架构。默认共享数据库、共享 Schema，通过 `tenant_id`、厂家归属字段、RBAC 和数据权限完成隔离。

核心原则：

1. 业务前台一套代码服务厂家租户和经销商租户。
2. 平台后台独立应用、独立部署、独立登录态。
3. 厂家不能访问其他厂家及其经销商数据。
4. 经销商只能访问自己租户内的数据。
5. 平台后台只做平台管理，不操作业务单据。
6. 预留独立部署能力，但第一期只实现共享部署。

---

### 2. 逻辑分层

| 层级 | 说明 | 数据边界 |
|---|---|---|
| 平台运营方 | 系统提供方，使用平台后台 | 管理所有厂家、经销商、配置、日志 |
| 厂家租户 | 使用系统的厂家 | 只能访问本厂家数据及归属本厂家的关系数据 |
| 经销商租户 | 某厂家下属经销商 | 只能访问本经销商租户业务数据 |

厂家租户下的 `dealers` 是厂家的客户主数据；经销商租户通过绑定关系关联其中一条 dealer 记录。该绑定不是数据授权，不代表厂家能查看经销商租户业务数据。

---

### 3. 部署与应用划分

#### 3.1 应用划分

| 应用 | 建议目录 | 入口 | 说明 |
|---|---|---|---|
| 业务前台 | `frontend-vue` | `/login` | 厂家和经销商业务用户使用 |
| 平台后台 | `admin-vue` | `/admin/`（未登录自动进入登录态） | 平台后台管理员使用；API 走 `/api/admin/auth/login` |
| 后端 API | `backend` | `/api/**`、`/api/admin/**` | 同时提供前台和平台后台接口 |

平台后台与业务前台必须使用不同登录接口和 token：

- 业务前台：`/api/auth/**`
- 平台后台：`/api/admin/auth/**`

#### 3.2 共享部署

第一期默认共享部署：

- 多厂家、多租户共用同一套前后端和数据库。
- 平台表、全局配置表不按租户隔离。
- 业务表通过 `tenant_id` 隔离。
- MinIO、Redis 按 key/object prefix 隔离。

#### 3.3 独立部署

后续独立部署时复用同一套代码，但独立配置：

- 独立数据库。
- 独立 Redis。
- 独立 MinIO bucket 或独立对象存储。
- 独立域名和部署环境。
- 通过部署配置标记部署模式。

数据模型预留 `deployment_mode`，第一期不实现独立部署控制台。

---

### 4. 租户上下文

后端通过 `TenantContext` 保存当前请求上下文：

- `tenantId`
- `userId`
- `username`
- `tenantType`
- `ownerManufacturerId`
- `userType`
- `authSource`（前台 / 平台后台）

上下文来源：

- 业务前台：从业务 token 解析。
- 平台后台：从后台 token 解析，不设置业务租户上下文。
- 不允许前端直接传 `tenantId` 决定数据范围。

请求结束后必须清理 ThreadLocal，避免线程复用污染。

---

### 5. 数据隔离规则

#### 5.1 表分类

| 表类型 | 示例 | 隔离规则 |
|---|---|---|
| 平台表 | 平台管理员、平台配置模板、全局字典 | 不参与租户过滤 |
| 租户主体表 | `tenants` | 按角色和权限访问 |
| 厂家归属关系表 | `tenant_dealer_bindings`、`product_mappings` | 必须带所属厂家条件 |
| 租户业务表 | `products`、`dealers`、订单、库存 | 必须按 `tenant_id` 隔离 |
| 日志表 | 操作日志、接口日志 | 平台可全局查；业务用户按租户查 |

#### 5.2 业务表要求

所有业务表必须包含：

- `tenant_id UUID NOT NULL`
- `created_at`
- `updated_at`
- `version`
- `deleted_at`（如需软删除）

经销商专属关系表还必须包含：

- `owner_manufacturer_id` 或可通过绑定关系稳定推导。

#### 5.3 查询和写入

- 查询：自动追加 `tenant_id = currentTenantId`。
- 新增：自动写入当前 `tenant_id`，忽略前端传入值。
- 更新：`WHERE id = ? AND tenant_id = ?`。
- 删除：同更新，必须带租户条件。
- 跨租户访问：抛出权限异常并记录安全日志。

#### 5.4 厂家访问经销商关系数据

厂家可访问：

- 归属自己的经销商租户只读列表。
- 自己与经销商之间的产品对码。

厂家不可访问：

- 经销商租户内的订单、库存、客户、采购、销售、手术报告、报表等业务数据。
- 其他厂家及其经销商的数据。

---

### 6. 缓存隔离

Redis key 必须带明确前缀：

- 业务前台 token：`dms:auth:{tenantId}:{userId}:{tokenId}`
- 平台后台 token：`dms:admin:auth:{userId}:{tokenId}`
- 租户状态：`dms:tenant:status:{tenantId}`
- 全局字典：`dms:cfg:dict:*`
- 页面配置：`dms:cfg:page:*`
- 产品对码：`dms:mapping:{manufacturerTenantId}:*`

租户停用时需要清理或吊销该租户 token 版本。

---

### 7. MinIO 存储隔离

报文文件、导入文件和导出文件按环境和租户分层：

```text
dms-{env}/
  api-logs/{yyyy}/{MM}/{dd}/{requestId}-req.json
  dms-{env}/
  api-logs/{yyyy}/{MM}/{dd}/{requestId}-resp.json
  product-mapping-imports/{manufacturerTenantId}/{batchId}/input.xlsx
  product-mapping-imports/{manufacturerTenantId}/{batchId}/errors.xlsx
```

第一期接口报文路径建议：

- bucket：`dms` 或按环境拆 bucket。
- 请求报文：`api-logs/{yyyy}/{MM}/{dd}/{requestId}-req.json`
- 响应报文：`api-logs/{yyyy}/{MM}/{dd}/{requestId}-resp.json`

下载报文文件必须经过平台后台权限校验，不允许公开直链。

---

### 8. 安全要求

1. 平台后台和业务前台 token 不能互换。
2. 停用租户后，该租户已有 token 立即失效。
3. 租户编码全局唯一。
4. 用户名为“租户内唯一”；平台后台管理员全局唯一。
5. 平台后台管理员不通过业务接口访问业务数据。
6. 所有平台写操作、租户开通、停用、重置密码必须记录审计日志。
7. 所有跨租户访问尝试记录安全日志。
8. 日志中的密码、token、Authorization、secret、手机号、身份证必须脱敏。

---

### 9. 第一期不做

- 不做模拟登录。
- 不做厂家查看经销商真实业务数据。
- 不做独立部署控制台。
- 不做租户级自定义页面布局。
- 不做租户级字典。
- 不做有效期自动到期。
- 不做计费、套餐计量和资源配额扣费。

## 二、角色权限与 RBAC 设计


﻿# 角色权限与 RBAC 设计

**版本**：v1.0  
**日期**：2026-08-02

---

### 1. 设计目标

业务前台权限统一采用 RBAC：用户关联角色，角色关联菜单/功能权限和数据权限。平台后台第一期只有固定后台管理员，不做平台后台 RBAC。

需要同时满足：

- 厂家租户和经销商租户功能基本一致。
- 厂家可见功能范围大于等于经销商。
- 租户管理员可在平台授权范围内自建角色。
- 客服可看租户全部数据。
- 销售只能看自己和下级岗位负责的经销商/客户数据。
- 基础数据是否可见由菜单/功能权限决定，业务单据再叠加数据权限。

---

### 2. 角色分类

| 角色编码 | 名称 | 适用租户 | 默认数据权限 |
|---|---|---|---|
| `MANUFACTURER_ADMIN` | 厂家管理员 | 厂家租户 | 租户所有数据 |
| `MANUFACTURER_SERVICE` | 厂家客服 | 厂家租户 | 租户所有数据 |
| `MANUFACTURER_SALES` | 厂家销售 | 厂家租户 | 自己及下级岗位数据 |
| `DEALER_ADMIN` | 经销商管理员 | 经销商租户 | 租户所有数据 |
| `DEALER_SERVICE` | 经销商客服 | 经销商租户 | 租户所有数据 |
| `DEALER_SALES` | 经销商销售 | 经销商租户 | 自己及下级岗位数据 |

默认角色由平台后台维护模板，开通租户时复制到租户内。租户管理员可以自建角色，但只能选择平台已授权给该租户的菜单和功能权限点。

---

### 3. 权限模型

建议基于现有表扩展：

- `resources`：菜单、按钮、API 权限点。
- `roles`：租户内角色。
- `role_resources` 或现有 `strategy_resources`：角色与权限点关系。
- `user_roles`：用户与角色关系。
- `role_data_policies`：角色数据权限配置。
- `users`：用户归属租户。

第一期可以保留现有 `strategies` 作为权限策略模型，但文档层面统一按“角色直接关联资源和数据权限”描述；实现时可逐步重构，避免大范围影响现有功能。

---

### 4. 权限点编码

权限点按“模块:资源:操作”命名：

| 类型 | 示例 | 说明 |
|---|---|---|
| 菜单 | `product:menu` | 产品管理菜单 |
| 页面 | `product:list:view` | 产品列表页 |
| 按钮 | `product:create` | 新建产品 |
| 按钮 | `product:update` | 编辑产品 |
| 按钮 | `product:delete` | 删除产品 |
| API | `api:POST:/api/products` | 后端接口权限 |
| 字段 | `product:field:costPrice` | 字段级权限预留 |
| 导出 | `product:export` | 导出权限 |

后端必须以 API 权限为准，前端隐藏菜单和按钮只作为体验优化。

---

### 5. 数据权限类型

| 编码 | 名称 | 说明 |
|---|---|---|
| `ALL_TENANT` | 租户所有数据 | 可访问当前租户所有数据 |
| `SELF_CREATED` | 自己创建的数据 | 只访问 `created_by = currentUserId` 的数据 |
| `POSITION_TREE` | 自己及下级岗位数据 | 销售岗位适用，按岗位树和负责经销商/客户过滤 |

用户拥有多个角色时，数据权限取并集。例如用户同时是客服和销售，则可看租户全部数据。

---

### 6. 销售岗位数据权限

现有岗位与经销商负责关系保持不变。销售岗位过滤逻辑：

1. 获取当前用户所属岗位。
2. 递归获取当前岗位及所有下级岗位 ID。
3. 查询这些岗位负责的 dealer/customer ID。
4. 对销售订单、销退出库、手术报告、合同、促销、经销商画像等单据按负责的 dealer/customer 过滤。

岗位树规则：

- 一个用户第一期默认属于一个主岗位。
- 岗位上下级使用现有岗位树。
- 岗位和 dealer/customer 的负责关系使用现有关系，不重新设计。
- 上级岗位可以查看自身及所有下级岗位负责的数据。

---

### 7. 权限校验流程

#### 7.1 登录后加载权限

1. 用户登录。
2. 后端查询用户角色。
3. 查询角色对应菜单、按钮、API 权限点。
4. 查询角色数据权限。
5. 返回 token 和权限快照，或由前端通过 `/api/auth/me` 加载。

#### 7.2 请求鉴权

1. 解析 token，得到 `tenantId`、`userId`、`userType`。
2. 加载用户角色与权限点。
3. 校验接口所需权限点。
4. 设置 `TenantContext`。
5. 数据查询层按数据权限自动拼接条件。

#### 7.3 管理边界

- 平台后台管理员创建租户管理员。
- 租户管理员创建普通用户和角色。
- 租户管理员不能创建平台权限，也不能超出平台给租户授权的菜单范围。
- 每租户只能有一个启用中的租户管理员。

---

### 8. 平台后台权限

第一期平台后台只有固定管理员账号，不做角色管理。

固定管理员可操作：

- 厂家租户、经销商租户管理。
- 租户绑定 dealer。
- 租户管理员创建、停用、重置密码。
- 默认角色模板、菜单模板、页面字段模板、筛选模板。
- 全局字典。
- 全平台日志中心。
- 缓存刷新和基础运维。

所有平台后台操作都记录操作日志。

## 三、租户开通与经销商绑定设计


﻿# 租户开通与经销商绑定设计

**版本**：v1.0  
**日期**：2026-08-02

---

### 1. 目标

平台后台负责创建厂家租户、经销商租户，以及经销商租户与厂家 dealer 主数据的一对一绑定。每个租户必须有且只有一个启用中的租户管理员。

---

### 2. 开通前置条件

#### 2.1 厂家租户开通前置

- 平台后台管理员已存在。
- 全局字典、默认角色、默认菜单、页面字段和筛选配置已初始化。
- 厂家编码全局唯一。

#### 2.2 经销商租户开通前置

- 所属厂家租户已创建且启用。
- 厂家已在自己的前台维护好对应 dealer 主数据。
- 该 dealer 尚未绑定其他启用中的经销商租户。
- 经销商租户编码全局唯一。
- 租户管理员用户名在该租户内唯一，建议全局也校验避免混淆。

平台后台只能选择厂家已有 dealer，不直接创建业务 dealer 主数据。

---

### 3. 厂家租户开通流程

1. 平台后台进入租户管理。
2. 新增厂家租户，填写编码、名称、联系人、联系方式、部署模式。
3. 系统创建 `tenants` 记录，类型为 `MANUFACTURER`。
4. 系统创建唯一厂家租户管理员。
5. 系统复制厂家默认角色模板。
6. 系统应用厂家默认菜单、页面字段、筛选项配置。
7. 系统加载全局字典。
8. 记录开通审计日志。
9. 返回初始密码，并要求租户管理员首次登录修改。

---

### 4. 经销商租户开通流程

1. 平台后台选择所属厂家租户。
2. 从该厂家租户的未绑定 dealer 列表中选择一个 dealer。
3. 填写经销商租户编码、名称、联系人、管理员账号。
4. 系统校验：
   - 厂家租户存在且启用。
   - dealer 属于该厂家。
   - dealer 未被其他启用中租户绑定。
   - 租户编码全局唯一。
5. 创建经销商租户，类型为 `DEALER`，写入所属厂家租户 ID。
6. 创建 `tenant_dealer_bindings` 绑定关系。
7. 创建唯一经销商租户管理员。
8. 复制经销商默认角色模板。
9. 应用经销商默认菜单、页面字段、筛选项配置。
10. 加载全局字典。
11. 记录开通审计日志。
12. 返回初始密码，并要求首次登录修改。

整个开通过程必须在一个事务内完成。任一步失败则回滚。

---

### 5. 绑定规则

- 一个经销商租户只能绑定一个 dealer。
- 同一厂家下一个 dealer 只能绑定一个启用中的经销商租户。
- 不同厂家下的 dealer 互不影响。
- 绑定后不支持解绑或换绑。
- 绑定错误时，停用错误租户，再重新创建正确租户。
- 停用的历史绑定保留，用于审计。
- 如果 dealer 在厂家租户内被停用，不影响已开通经销商租户登录；但是否允许重新绑定需按“未被启用租户绑定”判断。

---

### 6. 租户状态管理

状态仅支持：

| 状态 | 说明 |
|---|---|
| `active` | 正常使用 |
| `inactive` | 停用，禁止登录，token 失效 |

操作：

- 启用租户：租户内用户可重新登录。
- 停用租户：所有用户禁止登录，已有 token 立即失效。
- 不物理删除租户。
- 第一期不做有效期自动到期。

停用时写入：

- `status = inactive`
- `disabled_at`
- `disabled_by`
- `disable_reason`

启用时清空停用字段。

---

### 7. 租户管理员管理

- 每租户有且仅有一个启用中的租户管理员。
- 平台后台管理员可以创建租户管理员。
- 平台后台管理员可以停用租户管理员。
- 平台后台管理员可以重置租户管理员密码。
- 租户管理员被停用或离职时，平台后台创建新的租户管理员后，旧管理员应停用。
- 租户管理员首次登录必须修改密码。
- 重置密码后必须再次强制修改密码。

建议在 `users` 中使用 `user_type` 和角色编码区分租户管理员，不新增独立管理员表。

### 8. 厂家可见经销商租户列表

- 经销商租户编码
- 经销商租户名称
- 绑定的 dealer 编码
- 绑定的 dealer 名称

## 六、产品主数据对码设计


﻿# 产品主数据对码设计

**版本**：v1.0  
**日期**：2026-08-02

---

### 1. 目标

厂家和经销商各自维护自己的产品主数据。产品对码用于建立某厂家产品与该厂家下属经销商产品之间的一对一关系。第一期只维护对码关系，主要服务报表汇总，不做跨租户业务单据查询，不做厂家实时查看经销商订单和库存。

---

### 2. 维护入口

产品对码放在厂家租户前台，不放在平台后台。

- 厂家管理员、客服或有权限的厂家角色可维护。
- 厂家只能选择归属自己的经销商租户。
- 厂家只能选择自己的产品和经销商产品。
- 经销商租户不维护对码。
- 平台后台不维护具体业务对码。

厂家前台需要提供“归属本厂家的经销商租户只读列表”，用于对码导入和查询。

---

### 3. 对码规则

- 厂家产品与经销商产品必须一对一。
- 一个厂家产品不能对码同一经销商的多个产品。
- 一个经销商产品不能对码同一厂家的多个产品。
- 一个对码关系必须明确厂家租户和经销商租户。
- 对码关系支持启用、停用。
- 停用的对码不参与报表汇总。
- 同一经销商租户下，经销商产品编码必须可唯一匹配一个产品。
- 对码不改变双方产品主数据归属。

---

### 4. 页面功能

厂家前台产品对码页面建议包含：

- 按经销商租户筛选。
- 按厂家产品编码/名称筛选。
- 按经销商产品编码/名称筛选。
- 按状态筛选。
- 对码列表。
- 手工新增/编辑/停用。
- Excel 批量导入。
- 导入模板下载。
- 错误报告下载。
- 导出对码结果。

---

### 5. Excel 导入

#### 5.1 模板字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 经销商租户编码 | 是 | 必须归属当前厂家 |
| 经销商产品编码 | 是 | 经销商租户内产品编码 |
| 厂家产品编码 | 是 | 当前厂家租户内产品编码 |
| 包装单位 | 否 | 预留报表换算 |
| 换算率 | 否 | 预留报表换算 |
| 备注 | 否 | 说明 |

#### 5.2 导入流程

1. 下载模板。
2. 上传 Excel。
3. 后端解析并生成导入批次。
4. 预览成功数据和错误数据。
5. 用户确认后正式写入。
6. 返回成功数量、失败数量、错误报告。

#### 5.3 校验规则

- 经销商租户存在、启用且归属当前厂家。
- 厂家产品存在且属于当前厂家。
- 经销商产品存在且属于该经销商租户。
- 同一厂家产品未与该经销商其他产品对码。
- 同一经销商产品未与该厂家其他产品对码。
- Excel 内行不能重复。
- 包装单位和换算率格式正确。
- 停用状态只能使用允许值。

导入时需要事务控制。单条失败是否整批失败：第一期建议“预览阶段全部校验，确认导入时有效数据入库、错误数据出报告”，但为了数据清晰，也可以整批失败。建议采用前者。

---

### 6. 报表用途

对码关系用于后续报表按厂家产品口径汇总经销商数据。第一期只维护关系，不实现跨租户数据同步。

后续报表汇总时需要注意：

- 只统计启用状态对码。
- 只处理归属当前厂家的经销商租户。
- 按包装单位和换算率做数量换算。
- 未对码产品进入异常清单。

---

### 7. 审计

以下操作记录业务操作日志：

- 新增对码。
- 编辑对码。
- 启用/停用对码。
- 批量导入。
- 导出对码。

日志需要记录厂家租户、经销商租户、厂家产品、经销商产品、操作人和操作时间。

## 七、日志审计与监控中心设计


﻿# 日志审计与监控中心设计

**版本**：v1.0  
**日期**：2026-08-02

---

### 1. 目标

平台后台提供全局日志中心，覆盖操作日志、登录日志、接口日志、异常日志和慢接口日志。第一期做应用级日志，不纳入服务器 CPU、内存、磁盘等基础设施指标。

现有 `op_log`、`api_call_log`、`user_login_logs`、`audit_logs` 可复用，但接口报文需要按新要求改为“元数据入库 + 原始报文文件入 MinIO”。

---

### 2. 日志类型

| 类型 | 说明 | 来源 |
|---|---|---|
| 操作日志 | 业务新增、编辑、删除、导入导出、审批等 | AOP/服务层 |
| 登录日志 | 登录成功、失败、退出、token 刷新 | Auth 服务 |
| 接口日志 | HTTP 请求响应、状态码、耗时 | Filter/Interceptor |
| 异常日志 | 业务异常、系统异常、堆栈 | 全局异常处理 |
| 慢接口日志 | 超过阈值的接口 | 接口日志派生 |
| 平台审计日志 | 租户开通、停用、重置密码、配置变更 | 平台后台 |

---

### 3. 接口日志存储

#### 3.1 数据库元数据

接口日志表记录：

- 请求 ID
- Trace ID
- 租户 ID、租户名称
- 厂家归属 ID（经销商请求时）
- 用户 ID、用户名
- 请求来源：前台/平台后台
- HTTP 方法
- 请求路径
- Query 参数摘要
- HTTP 状态码
- 业务 code
- 成功/失败
- 耗时毫秒
- 客户端 IP
- User-Agent
- 请求开始/结束时间
- 异常摘要
- 请求报文文件路径
- 响应报文文件路径
- 请求文件大小
- 响应文件大小
- 是否慢接口

#### 3.2 原始报文文件

原始请求和响应报文存储到 MinIO：

- 请求文件：`api-logs/{yyyy}/{MM}/{dd}/{requestId}-req.json`
- 响应文件：`api-logs/{yyyy}/{MM}/{dd}/{requestId}-resp.json`

报文文件内容建议 JSON：

```json
{
  "requestId": "uuid",
  "method": "POST",
  "path": "/api/products",
  "headers": {},
  "query": {},
  "body": {}
}
```

下载文件必须经过平台后台鉴权，不能生成公开永久链接。

---

### 4. 列表筛选

平台后台日志列表支持：

- 日志类型
- 租户
- 厂家归属
- 用户
- 请求路径
- HTTP 方法
- HTTP 状态码
- 业务成功/失败
- 时间范围
- 请求 ID
- Trace ID
- 最小耗时
- 是否慢接口

操作日志还支持按业务类型、业务 ID、操作人、操作动作筛选。

---

### 5. 报文处理规则

#### 5.1 记录内容

记录：

- 请求头中与排查有关的字段，如 `Content-Type`、`User-Agent`、`X-Request-Id`。
- Query 参数。
- 请求体。
- 响应体。
- 异常摘要和堆栈。

不记录或只记录元数据：

- 文件上传二进制。
- 文件下载二进制。
- 图片、PDF、Excel 原始二进制。
- 超过阈值的超大文本，保留截断摘要。

建议阈值：

- 普通文本报文超过 1MB 截断或仅存文件。
- 二进制请求不存 body。
- 响应为文件流时只记录文件元数据。

#### 5.2 脱敏

必须脱敏：

- `password`
- `token`
- `accessToken`
- `refreshToken`
- `Authorization`
- `secret`
- 手机号
- 身份证

脱敏策略：

- 手机号保留前 3 后 4。
- 身份证保留前 3 后 4。
- 密码和 token 替换为 `******`。
- 递归处理 JSON 嵌套字段和 Header。

---

### 6. 慢接口

第一期可由接口日志派生：

- 普通接口慢阈值默认 1000ms。
- 报表/导入导出可单独配置阈值，例如 5000ms。
- 超过阈值标记 `slow = true`。
- 平台后台可单独筛选慢接口。

阈值先写配置，不做复杂页面。

---

### 7. 保留与清理

| 数据 | 保留周期 |
|---|---|
| 日志元数据 | 1 年 |
| 原始报文文件 | 90 天 |
| 异常日志 | 180 天 |
| 平台审计日志 | 1 年以上，建议永久或按合规要求 |

清理任务：

- 每天按创建时间清理过期元数据。
- 删除元数据前先删除对应 MinIO 文件，或按对象前缀清理。
- 记录清理任务执行日志。

---

### 8. 平台审计重点

平台后台以下操作必须审计：

- 厂家租户创建、停用、启用。
- 经销商租户创建、停用、启用。
- dealer 绑定。
- 租户管理员创建、停用、重置密码。
- 默认角色、菜单、页面字段、筛选配置修改。
- 全局字典修改。
- 缓存刷新。
- 日志文件下载。

审计日志需要记录变更前后值。

---

### 9. 与现有日志表关系

- `op_log`：现有全链路日志，可作为接口日志基础，后续扩展字段并移除大字段入库。
- `api_call_log`：面向外部接口调用，继续保留用于入站/出站 API。
- `user_login_logs`：继续作为登录日志。
- `audit_logs`：用于业务审计。
- 平台后台新增统一日志查询页，后续可逐步收敛展示。

## 八、平台后台数据库设计


﻿# 数据库设计

**版本**：v1.0  
**日期**：2026-08-02

---

### 1. 设计原则

- 共享数据库、共享 Schema，业务表通过 `tenant_id` 隔离。
- 经销商租户必须归属一个厂家租户。
- `dealers` 是业务客户主数据，不作为租户表。
- 平台表不参与租户过滤。
- 所有新增表包含审计字段。
- 现有 V1–V49 表尽量增量扩展，避免破坏性重建。

---

### 2. `tenants` 扩展

现有 `tenants` 表需要补充：

| 字段 | 类型 | 说明 |
|---|---|---|
| `tenant_type` | VARCHAR(16) NOT NULL DEFAULT 'DEALER' | `MANUFACTURER` / `DEALER` |
| `owner_manufacturer_id` | UUID | 经销商租户归属厂家；厂家租户为空 |
| `deployment_mode` | VARCHAR(16) NOT NULL DEFAULT 'SHARED' | `SHARED` / `DEDICATED` |
| `disabled_at` | TIMESTAMPTZ | 停用时间 |
| `disabled_by` | BIGINT | 停用人 |
| `disable_reason` | VARCHAR(500) | 停用原因 |
| `enabled_at` | TIMESTAMPTZ | 最近启用时间 |

索引：

- `idx_tenants_type_status(tenant_type, status)`
- `idx_tenants_owner(owner_manufacturer_id, status)`

现有固定租户 `11111111-1111-1111-1111-111111111111` 应迁移为厂家租户。

### 3. 租户经销商绑定表 `tenant_dealer_bindings`

```sql
CREATE TABLE tenant_dealer_bindings (
    id BIGSERIAL PRIMARY KEY,
    dealer_tenant_id UUID NOT NULL REFERENCES tenants(id),
    manufacturer_tenant_id UUID NOT NULL REFERENCES tenants(id),
    dealer_id BIGINT NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'active',
    bound_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    bound_by BIGINT,
    unbound_at TIMESTAMPTZ,
    remark VARCHAR(500),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    version INT NOT NULL DEFAULT 0,
    deleted_at TIMESTAMPTZ
);
```

约束和索引：

- 一个经销商租户只能有一个未删除绑定：唯一索引 `ux_tdb_dealer_tenant`。
- 同一厂家下一个 dealer 只能有一个启用绑定：部分唯一索引。
- `idx_tdb_manufacturer(manufacturer_tenant_id, status)`。
- `idx_tdb_dealer(manufacturer_tenant_id, dealer_id)`。

`dealer_id` 不加外键，因为 `dealers.id` 属于业务租户表且跨租户引用主要用于关系绑定；应用层必须校验 dealer 属于厂家租户。

### 4. 用户表调整

`users` 继续复用。需要关注：

- `tenant_id` 必填。
- 平台后台管理员可归属一个固定平台租户，或使用 `user_type='PLATFORM_ADMIN'` 且独立登录。
- 租户管理员通过角色识别，不新增管理员表。
- 每租户只能有一个启用中的租户管理员，建议用部分唯一索引或应用事务保证。

建议字段：

- `user_type` 扩展支持：`MANUFACTURER_USER`、`DEALER_USER`、`PLATFORM_ADMIN`。
- 如继续使用旧值 `vendor/dealer`，需要兼容并逐步迁移。
- 增加 `last_password_reset_at`，如现有字段不足。

### 1. 接口分层

| 层级 | 前缀 | 认证 | 说明 |
|---|---|---|---|
| 平台后台 | `/api/admin/**` | 后台 token | 平台管理员使用 |
| 业务前台 | `/api/**` | 业务 token | 厂家和经销商租户使用 |
| 对外开放接口 | `/api/open/**` | AppKey/签名 | 后续外部系统接入 |

平台后台和业务前台 token 不能互换。平台接口统一经过后台鉴权过滤器；业务接口统一经过租户鉴权和数据权限过滤器。

### 3. 租户管理 API

#### 厂家租户

- `GET /api/admin/tenants/manufacturers`：厂家租户分页列表。
- `POST /api/admin/tenants/manufacturers`：创建厂家租户。
- `GET /api/admin/tenants/manufacturers/{id}`：厂家租户详情。
- `POST /api/admin/tenants/{id}/enable`：启用。
- `POST /api/admin/tenants/{id}/disable`：停用。

创建厂家请求：

```json
{
  "code": "MFR_A",
  "name": "厂家A",
  "contactName": "张三",
  "contactPhone": "13800000000",
  "adminUsername": "mfr_admin",
  "adminPassword": "初始化密码",
  "adminName": "厂家管理员"
}
```

#### 经销商租户

- `GET /api/admin/tenants/dealers`：经销商租户分页列表。
- `POST /api/admin/tenants/dealers`：创建经销商租户并绑定 dealer。
- `GET /api/admin/tenants/dealers/{id}`：详情。
- `GET /api/admin/tenants/{id}/bindings`：绑定信息。
- `POST /api/admin/tenants/{id}/enable`：启用。
- `POST /api/admin/tenants/{id}/disable`：停用。

创建经销商请求：

```json
{
  "manufacturerTenantId": "uuid",
  "dealerId": 1001,
  "code": "DEALER_A",
  "name": "经销商A",
  "contactName": "李四",
  "contactPhone": "13900000000",
  "adminUsername": "dealer_admin",
  "adminPassword": "初始化密码",
  "adminName": "经销商管理员"
}
```

后端必须校验 dealer 属于该厂家且未被启用中租户绑定。
