# 排障手册

## 1. 排障总流程

遇到问题时按以下顺序定位：

1. 确认问题发生在哪个端：业务前端、平台后台、移动端、后端、数据库还是网关。
2. 复现问题，记录账号、租户、时间、请求路径、请求参数和截图。
3. 打开浏览器开发者工具，查看请求 URL、状态码、响应体和请求头。
4. 查看后端日志，定位异常栈、SQL、当前用户和租户信息。
5. 检查 Nginx access/error 日志是否有 499、502、504 或超时。
6. 检查数据库连接、慢查询、锁等待和数据状态。
7. 检查 Redis、MinIO 和外部依赖是否可用。
8. 确认最近发布、配置变更和数据修复。

不要在没有备份和评估的情况下直接改生产数据。

## 2. 登录失败

### 常见原因

- 账号或密码错误。
- 首次登录需要强制修改密码。
- 用户被禁用或租户被停用。
- JWT 密钥变化导致旧 Token 无法使用。
- 后端连接了错误数据库。
- 微信登录使用了错误 AppID 或 Secret。
- Nginx 没有转发 Authorization 头。

### 定位步骤

1. 在浏览器 Network 中查看登录接口返回码和错误信息。
2. 查看后端登录接口日志。
3. 确认数据库中用户状态、密码哈希、租户状态。
4. 检查 `JWT_SECRET` 是否和其他实例一致。
5. 检查 Nginx 配置是否代理 `/api/auth/` 和 `/auth/`。
6. 微信登录检查 `WECHAT_APP_ID`、`WECHAT_APP_SECRET` 和回调地址。

## 3. 接口 500

### 定位步骤

1. 在浏览器 Network 中拿到请求路径和请求参数。
2. 在后端日志中搜索同一时间点的异常栈。
3. 判断是参数异常、空指针、数据库约束、权限问题还是外部依赖超时。
4. 如果是 SQL 异常，检查 Flyway 脚本、字段长度、非空约束、唯一约束。
5. 如果是外部接口异常，检查目标地址、凭证、超时和返回格式。
6. 修复后先在测试环境复现并验证。

### 注意

- 不要只把异常 catch 住而不处理根因。
- 不要在生产打开全量 SQL 日志长期运行。
- 500 问题要记录成 FAQ，避免重复排查。

## 4. 接口 401 或 403

### 401 未认证

检查：

- Token 是否存在。
- Token 是否过期。
- Authorization 头是否被 Nginx 转发。
- 后端 JWT 密钥是否一致。
- 用户是否被删除或禁用。

### 403 无权限

检查：

- 当前账号角色。
- 菜单、按钮和接口权限绑定。
- 数据权限和租户范围。
- 后端接口是否加了权限注解或授权校验。
- 前端按钮隐藏不等于后端安全，必须以后端校验为准。

## 5. 页面空白或资源 404

检查：

- 前端构建产物是否完整发布。
- 平台后台是否发布到 `/admin/` 目录。
- Nginx 是否配置 SPA 回退：`try_files ... /index.html`。
- 静态资源路径是否使用了正确 base。
- 浏览器缓存是否未刷新。

业务前端通常需要：

- `/` 回退到 `/index.html`

平台后台通常需要：

- `/admin/` 回退到 `/admin/index.html`

## 6. 跨域或接口代理错误

本地开发检查：

- `frontend-vue/vite.config.js` 中 `/api`、`/auth` 代理目标。
- `admin-vue/vite.config.js` 中 `/api` 代理目标。
- `VITE_API_TARGET` 是否正确。
- 后端是否启动在 8080。

测试/生产检查：

- 是否由 Nginx 同源代理，而不是浏览器直连后端。
- Nginx 是否配置了必要的 proxy header。
- 后端 CORS 配置是否和实际域名一致。

## 7. 数据库连接失败

检查：

- `DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`。
- PostgreSQL 是否启动。
- 防火墙和网络策略。
- 数据库用户权限。
- 连接池是否耗尽。
- 数据库磁盘是否满。

如果使用 Docker，确认容器是否在同一网络，不要误用 `localhost` 访问宿主机服务。

## 8. Flyway 迁移失败

### 常见原因

- 迁移版本号重复。
- SQL 语法错误。
- 字段、表或数据已存在。
- 数据库用户权限不足。
- 历史失败记录残留在 `flyway_schema_history`。

### 处理步骤

1. 查看后端启动日志中的 Flyway 错误。
2. 确认失败脚本版本。
3. 备份数据库。
4. 在测试环境复现并修复脚本。
5. 对生产环境只新增修复迁移，不直接修改已发布脚本。
6. 如确需人工处理 `flyway_schema_history`，必须由熟悉迁移状态的人执行。

## 9. Redis 相关问题

症状可能包括：

- 登录状态异常。
- 分布式锁不释放。
- 缓存数据不一致。
- 接口超时。

检查：

- `REDIS_HOST`、`REDIS_PORT`、`REDIS_PASSWORD`、`REDIS_DB`。
- Redis 是否内存满或被驱逐 key。
- 是否有业务 key 没有设置过期时间。
- 是否误清空了整个 database。
- 是否和其他系统共用 Redis database。

清缓存前必须确认 key 前缀和影响范围。

## 10. 文件上传下载失败

检查：

- 后端文件大小限制：默认 50MB。
- Nginx `client_max_body_size`：示例为 30MB。
- MinIO endpoint、access key、secret key、bucket。
- 服务器和 MinIO 之间网络。
- 文件权限和访问路径。
- 文件名是否包含特殊字符。

上传成功但无法下载时，还要检查：

- 文件是否真正写入 MinIO。
- 访问 URL 是否需要鉴权。
- 业务数据中保存的路径是否正确。

## 11. 数据串租户或越权

这是高优先级风险。发现后立即：

1. 停止相关写操作或临时下线入口。
2. 记录涉及的租户、用户、时间和数据范围。
3. 备份数据库。
4. 检查后端查询是否漏了租户条件。
5. 检查是否有原生 SQL 绕过租户过滤。
6. 检查后台接口是否误用平台权限读取业务数据。
7. 修复后用两个不同租户账号交叉验证。

不要只修页面显示，必须修后端查询和写入逻辑。

## 12. 性能变慢

定位步骤：

1. 确认是全局变慢还是单个接口变慢。
2. 检查服务器 CPU、内存、磁盘、网络。
3. 检查数据库慢查询和连接数。
4. 检查 Nginx 响应时间和 504。
5. 检查 Redis 是否命中率下降或不可用。
6. 检查是否有大批量导出、报表或定时任务。
7. 检查最近发布是否引入了 N+1 查询。

处理时优先止血，例如限流、降级、暂停大批量任务，再做根因优化。

## 13. 定时任务或异步任务失败

检查：

- 任务是否启用。
- 执行时间和频率。
- 任务日志。
- 上一次执行是否卡死或重复执行。
- 外部依赖是否超时。
- 数据库锁是否阻塞。

如果有分布式锁，确认锁是否被长期占用，以及异常时是否正确释放。

## 14. 发版后异常

按以下顺序判断：

1. 前端是否加载了新版本资源。
2. 后端是否启动成功。
3. 健康检查是否通过。
4. Flyway 是否执行成功。
5. 环境变量是否指向正确环境。
6. Nginx 是否指向正确后端或静态目录。
7. 是否需要回滚。

如果影响主业务，优先回滚恢复服务，再在测试环境复现。

## 15. 每次故障后必须补充

处理完成后，在团队知识库中补充：

- 故障现象。
- 影响范围。
- 开始和恢复时间。
- 根因。
- 临时止血动作。
- 永久修复方案。
- 如何监控和预防。
- 是否需要更新本手册。
