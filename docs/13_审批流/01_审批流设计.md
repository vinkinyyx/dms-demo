# 审批流设计与使用说明

**当前版本**: v3.11.0
**最后更新**: 2026-08-09
**适用模块**: 销售订单、采购订单、销售退货、采购退货、合同、授权

---

## 1. 目标与范围

租户管理员可以为不同业务单据配置审批流，并应用到单据提交环节。核心能力：

- 按业务类型配置多套审批流，按条件（单据金额、单据类型等）自动匹配。
- 顺序节点审批；每个节点可配置多个审批人（账号或角色），支持“任一人通过 / 所有人通过”。
- 审批动作：同意、驳回、转办、前加签 / 后加签、撤回、抄送；管理员可改派、终止。
- 全局审批委托：有效期内某委托人的待办自动转交受托人。
- 审批流带版本：已在审批中的实例沿用提交时的快照版本，新提交的单据使用最新已发布版本。
- 驳回策略可配：退回发起人修改后重新提交，或直接作废。
- 未匹配到任何审批流时，单据默认“自动审批通过”，不阻断提交。
- 通知：站内信 + 邮件（163 SMTP）；飞书卡片审批预留接口，暂未启用。

---

## 2. 核心概念

| 概念 | 说明 |
|---|---|
| 审批模板 Template | 某业务类型下的一套审批流定义，含条件、节点、审批人、抄送、驳回策略；有版本号。 |
| 模板类型 templateType | `MANUAL` 人工审批；`AUTO_APPROVE` 匹配后直接自动通过。 |
| 条件 conditionConfig | `{ "logic": "AND|OR", "rules": [{field, operator, value}] }`，决定单据是否命中该模板。 |
| 优先级 priority | 数值越大越优先；同业务类型按 priority desc, version desc, id desc 取第一个命中的已启用模板。 |
| 节点 Node | 审批的一个环节，按 nodeOrder 顺序执行；节点上配审批人、抄送人、多人审批方式、是否允许转办/加签、超时。 |
| 审批人 Assignee | 类型 `USER`（账号）或 `ROLE`（角色，解析为该角色下全部用户）。 |
| 实例 Instance | 一张单据提交后产生的一次审批过程，固化模板快照。 |
| 任务 Task | 节点上每个审批人对应一条待办任务。 |
| 记录 Record | 实例上的完整操作流水（提交、同意、驳回、转办、加签、撤回、终止、自动通过等）。 |
| 抄送 CcRecord | 节点完成或流程结束时抄送相关人员。 |
| 委托 Delegation | 全局委托关系，任务生成时若审批人在委托期内，任务转交给受托人。 |

## 3. 状态机

### 3.1 实例状态（approval_instances.status）

| 状态 | 含义 |
|---|---|
| RUNNING | 审批中 |
| APPROVED | 审批通过（全部节点完成） |
| AUTO_APPROVED | 自动通过（命中自动审批模板，或无匹配模板） |
| REJECTED | 已驳回/已作废（驳回策略为 CANCEL） |
| RETURNED | 已退回发起人（驳回策略为 RETURN_TO_SUBMITTER） |
| WITHDRAWN | 发起人已撤回，单据回到草稿 |
| TERMINATED | 管理员终止 |

### 3.2 任务状态（approval_tasks.status）

| 状态 | 含义 |
|---|---|
| PENDING | 待处理 |
| APPROVED | 已同意 |
| REJECTED | 已驳回 |
| CANCELLED | 已取消（同节点他人已通过 ANY / 流程被终止等） |
| TRANSFERRED | 已转办 |
| TERMINATED | 随流程终止 |

### 3.3 与业务单据状态联动

- 提交订单：订单状态置为 `PENDING_APPROVAL`，生成审批实例。
- 审批通过 / 自动通过：订单置为 `APPROVED`，并自动生成下游草稿（销售订单→销售出库草稿；采购订单→收货入库草稿）。
- 驳回退回：订单回到 `DRAFT`，发起人修改后重新提交会生成**新的审批实例**。
- 驳回收回/作废：订单置为 `REJECTED`。
- 撤回：订单回到 `DRAFT`。
- 管理员终止：根据终止原因决定回到草稿或作废。

## 4. 条件匹配规则

`conditionConfig` 结构：

```json
{
  "logic": "AND",
  "rules": [
    { "field": "finalAmount", "operator": "GTE", "value": 50000 },
    { "field": "orderType",   "operator": "EQ",  "value": "NORMAL" }
  ]
}
```

- `logic`：`AND`（全部满足）或 `OR`（任一满足）。
- `field`：取自提交时传入的 `businessSnapshot`，常用字段：`finalAmount`（单据金额）、`orderType`（单据类型）、`dealerId`、`supplierId`。
- `operator`：

| 操作符 | 含义 | value 类型 |
|---|---|---|
| EQ | 等于（字符串比较） | 任意 |
| NE | 不等于 | 任意 |
| IN | 属于（集合） | 数组 |
| GT / GTE | 大于 / 大于等于 | 数值 |
| LT / LTE | 小于 / 小于等于 | 数值 |

- 条件为空（无 rules）表示匹配该业务类型的全部单据。
- 选择逻辑：同业务类型下，可配置高优先级的“小额自动通过”模板（无审批节点或 `AUTO_APPROVE`，条件如 `finalAmount LT 10000`），再配置普通审批模板作为兜底。

## 5. 审批节点与多人规则

- 节点按 `nodeOrder` 从 1 开始顺序执行，前一节点通过才进入下一节点。
- 每个节点的审批人由多个 USER/ROLE 组成：ROLE 会解析为该角色下所有用户，去重后逐人生成任务。
- `approveMode`：
  - `ANY`：任一人审批通过即节点通过，其余待办自动取消。
  - `ALL`：该节点全部审批人通过，节点才通过。
- 节点可单独配置是否允许转办 `allowTransfer`、加签 `allowAddSign`。
- 加签仅支持前加签与后加签：
  - 前加签：加签人审批通过后，原审批人继续审批。
  - 后加签：原审批人通过后，加签人再审批。
- 节点可配置抄送人（节点完成时通知）；流程可配置“完成抄送”（流程结束时通知）。
- 超时时长可在模板或节点上配置（当前仅存储与展示，超时提醒定时任务待实现）。

---

## 6. 驳回、撤回与重新提交

- 驳回策略在模板上配置：
  - `RETURN_TO_SUBMITTER`：退回发起人，单据回到草稿；发起人修改后重新提交，生成**新实例**，旧实例保留记录。
  - `CANCEL`：直接作废单据。
- 发起人可在审批中撤回，单据回到草稿。
- 重新提交始终生成新的审批实例，遵循最新已发布版本。

---

## 7. 版本管理

- 模板有 `versionNo`，状态为 `DRAFT / ENABLED / DISABLED。
- 新建模板为草稿（DRAFT），发布后变为 ENABLED 并写入 `publishedAt/publishedBy`。
- 对已启用模板点“新版本”会复制出一份新的草稿（versionNo + 1），不影响进行中的实例。
- 实例创建时把模板关键内容写入 `templateSnapshot`，后续模板修改或停用均不影响该实例。
- 同一业务类型可有多个 ENABLED 模板，按优先级 + 版本选择，用于按条件区分不同审批路径。

---
## 8. 管理员干预

拥有 `approval:admin` 权限的管理员可在“审批监控”中：

- 查看全部审批实例与审批记录。
- 改派（reassign）：将当前进行中的任务改交给其他人，原任务终止、生成新任务。
- 终止（terminate）：强制结束审批，并根据终止原因决定单据回到草稿还是作废。

## 9. 委托

- 全局委托：委托人在 `startsAt ~ endsAt` 有效期内产生的新待办，自动转交给受托人。
- 任务上记录 `delegatedFromUserId` 与 `originalAssigneeId`，审批记录保留委托痕迹。
- 可随时停用委托。

## 10. 超时提醒

- 待办任务根据节点 `timeoutHours` 计算 `dueAt`，到期后进入超时提醒扫描。
- 定时任务 `ApprovalTimeoutReminderTask` 默认每天 09:00 执行（cron: `0 0 9 * * ?`）。
- 默认提醒间隔 24 小时、最多提醒 3 次，可通过配置调整：
  - `dms.approval.reminder.enabled`（默认 true）
  - `dms.approval.reminder.cron`
  - `dms.approval.reminder.interval-hours`
  - `dms.approval.reminder.max-count`
- 超时仅发送邮件和站内提醒，不会自动同意或驳回。

## 11. 通知

- 通知分两路：站内信由 `ApprovalNotifier` 处理（待办生成、节点流转、通过、驳回、抄送等事件），邮件由 `ApprovalMailNotifier` 单独处理。
- 邮件走 163 SMTP（`smtp.163.com:465` SSL），发件人 `vinkinyu@163.com`，配置在 `application.yml`（`spring.mail.*` 与 `dms.mail.*`）。建议生产环境改用环境变量注入授权码，不要硬编码。
- 用户账号创建时手机号与邮箱均为必填；手机号用于未来对接飞书，邮箱用于接收审批邮件。

### 11.1 邮件发送日志

- 每一封审批邮件（待办、抄送、结果、超时提醒）以及“测试邮件”都会写入 `email_logs` 表，发送成功或失败均记录，便于排查“邮件有没有发、发给了谁”。
- 记录字段：租户、发件人 `from_address`、收件人 `to_address`、主题、正文、`status`（`SUCCESS`/`FAILED`）、`biz_type`（`APPROVAL_TASK`/`APPROVAL_CC`/`APPROVAL_RESULT`/`APPROVAL_REMINDER`/`TEST`）、`biz_id`（审批业务 ID）、收件人用户 ID、`error_message`、`sent_at`。
- 日志写入使用独立事务（`REQUIRES_NEW`），即使审批业务回滚，失败日志也不会丢失。
- 管理端查看路径：**用户与权限 → 邮件发送日志**，支持按状态筛选、分页查看。
- 发送测试邮件接口：`POST /api/email-logs/test`，请求体 `{"to":"收件人邮箱"}`，实际经 SMTP 发送并写入一条 `TEST` 日志，返回该日志记录（含 `status`）。
- 说明：通过 SMTP 客户端发出的邮件默认不会保存在 163 网页/客户端的“已发送”文件夹，这是正常现象；以 `email_logs` 中的 `SUCCESS` 记录和收件箱实际收件为准。

## 16. 合同业务类型接入（v3.11.0）

> 适用于 v3.11.0 重构后的合同模块（方案 A：合并申请/合同为单一实体 + 模板驱动）。

### 16.1 业务类型与实例

- 业务类型编码：`CONTRACT`（不变，承接合同申请时期）。
- 业务实例：`contracts`（主键 `id`）。
- `businessSnapshot`：审批中心向回调方下发的字段快照，含 `code` / `name` / `category` / `dealerId` / `dealerName` / `targetAmount` / `signedAmount` / `validFrom` / `validTo` / `status` / `applicationType`（NEW/MODIFY/RENEW/TERMINATE）/ `refContractId`。
- 审批详情展示使用 `form_data` 中 `approvalVisible=true` 的字段（与 `businessSnapshot` 共同呈现）。

### 16.2 状态映射（`ContractApprovalCallback`）

| 审批事件 | `contracts.status` | 其它动作 |
| --- | --- | --- |
| `onApproved` | `effective` | 写 `effective_at = now()`，`contract_revisions(action='approve', round=...)` |
| `onReturned` / `onRejected` | `rejected` | 写 `contract_revisions(action='reject', comment=意见)` |
| `onWithdrawn` | `draft` | 写 `contract_revisions(action='withdraw')` |
| `onTerminated`（终止审批通过） | `terminated` | 写 `terminated_at = now()` |

> 提交动作（`onSubmitted`）由 `ContractService.submit` 主动写入 `contract_revisions(action='submit', snapshot=form_data)`，并把 `contracts.status='pending'`。

### 16.3 审批详情三块布局（`ApprovalDetailDrawer.vue`）

1. **合同业务信息**（必填只读）：编号 / 名称 / 分类 / 经销商 / 目标金额 / 签约金额 / 有效期 / 状态 / 业务类型（NEW/MODIFY/RENEW/TERMINATE）。
2. **审批可见字段**（来自 `form_data` 中 `approvalVisible=true` 的字段，按 `group` 分组渲染）：便于审批人快速了解合同关键条款。
3. **审批时间线**：节点、审批人、意见、附件下载。

### 16.4 流程编排约束

- 单条合同只发起一个审批实例；变更/续签/终止通过 `applicationType` 区分，并在新建时带 `refContractId`。
- 提交后 `contracts.status='pending'`，前端锁定编辑；驳回回到 `rejected` 后可重新编辑并再次提交（`round` 递增）。
- 终止审批需基于 `effective` 状态的合同发起；通过后置 `terminated` 并清空 `source_file_id`（不删成稿文件本身）。

### 16.5 关键文件

- 后端：
  - `contract/entity/Contract.java`、`contract/entity/ContractRevision.java`
  - `contract/service/ContractService.java`（`submit` / `withdraw` / 状态守卫）
  - `contract/service/ContractApprovalCallback.java`（实现 `ApprovalCallback` 接口）
  - `contract/service/ContractExpiryTask.java`（每日扫 `valid_to` 到期置 `expired`）
- 前端：

  - `frontend-vue/src/views/contract/ContractEdit.vue`、`ContractDetail.vue`：提交/撤回/查看审批进度入口
