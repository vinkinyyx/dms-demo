# DMS 部署优化方案 v2（Fast/Full 双档流水线）

> **作者**：主 Agent（Dispatcher Guard） · **日期**：2026-07-26 · **版本**：draft-1
> **目的**：解决用户反馈"每次代码写完之后部署到服务器上总是特别慢"的痛点，将后端/前端热更新从 3-6 分钟压到 60-90 秒；同时保留铁律 1-8 的所有安全属性，并在每次部署完成后自动跑 browser-use 全链路验证。

---

## 一、问题根因（对照 `.trae/skills/dms-deploy/SKILL.md` 现状）

| # | 现状 | 单次耗时 | 根因 |
|---|---|---|---|
| 1 | 服务器上 `docker run maven:3.9 mvn clean package` | 3-6 min | 每次 `clean` 抛掉增量编译，即便挂 `/opt/dms/maven-repo` 冷网络仍慢 |
| 2 | 前端 Dockerfile 里再跑 `npm install + vite build` | 1-2 min | 依赖全量拉取，图省事直接从旧镜像 `docker cp dist` 又丢失可复现性 |
| 3 | `rm -rf backend-src && tar -xzf` 全量覆盖 | 30-60 s | 数万文件替换，Docker 层几乎不 hit cache |
| 4 | `docker builder prune -af` 硬清缓存（铁律 8） | 每次都做 | 与上一步双向掐死增量构建 |
| 5 | 后端启动固定 `sleep 90` | 90 s | 无健康探针轮询 |
| 6 | 后端/前端串行 | 累加 | 缺少并行编排 |

**合计**：一次"改一个 Java 文件 + 一个 Vue 文件"的完整部署，实测 4-7 分钟。

## 二、优化目标

| 指标 | 目标 | 现状 |
|---|---|---|
| Fast · 后端热更新 | ≤ 90 s | 4-6 min |
| Fast · 前端热更新 | ≤ 40 s | 2-3 min |
| 极速热替换 | ≤ 15 s | N/A |
| Full 全量部署 | ≤ 3 min | 5-7 min |
| 每次部署失败自动回滚 | ✅ | ❌ |
| 部署完成后自动 browser-use 全链路验证 | ✅ | ❌ |

## 三、优化策略（三档流水线 + 六项工程改进）

### 3.1 三档流水线

| 档位 | 触发条件 | 关键动作 | 目标 |
|---|---|---|---|
| **Hot · 极速热替换** | 只改前端 `dist` / 只改后端 jar | `docker cp` 到现有容器 → 前端 `nginx -s reload` / 后端 `docker restart` | ≤ 15 s |
| **Fast · 后端** | Java 源码变化，pom 未变 | 本地 `mvn -o -T 1C -DskipTests package` → 传 `app.jar` → `Dockerfile.runtime` 只 COPY jar → 重启 | ≤ 90 s |
| **Fast · 前端** | Vue 源码变化，package.json 未变 | 本地 `npm run build` → 传 `dist/` + `nginx-vue.conf` → 2 层 COPY 构建 → 重启 | ≤ 40 s |
| **Full · 完整** | pom.xml / package.json / Dockerfile / 迁移 变化 | 走当前完整流程，保留兼容性 | ≤ 3 min |

**选档决策**：以 `git diff --name-only <last-deploy-commit>` 判断，无需人工干预。

### 3.2 六项工程改进

1. **本地打包**：后端 `mvn -o -T 1C -DskipTests package` 用本地 `~/.m2` 缓存 + 并行 1 核 1 线；前端 `vite build`。
2. **hash 短路**：`sha256(app.jar) == 服务器已有` 则跳过上传/重启。
3. **并行编排**：后端本地构建与前端本地构建并行；服务器上后端构建期间同步跑前端 build。
4. **SSH 复用**：`plink -share` / MCP `ssh_execute` 一次多命令，减少握手；单次部署 SSH 命令数从 15+ 降到 4。
5. **健康探针轮询**：`while ! curl -sf localhost:8080/actuator/health; do sleep 2; done` 替代 `sleep 90`，正常 20-30 s 就位。
6. **失败自动回滚**：部署前 `docker tag dms-backend:latest dms-backend:rollback`；健康检查失败自动 `docker tag rollback → latest` 并 `docker restart`。

### 3.3 与铁律的兼容性

| 铁律 | v1 做法 | v2 做法 | 结论 |
|---|---|---|---|
| 1. 源码 100% 替换 | 上传 tar.gz + grep 抽查 | Fast 走 jar/dist 直接产物校验；Full 保持旧法 | ✅ 更强 |
| 2. 旧镜像必须删除 | `docker rmi` | Fast 每次 build 用不同 tag（`:v3.7.2-{sha}`），Full 保持删除 | ✅ 更强 |
| 3. 校验最终产物 | `docker exec grep` | 保留，且新增 sha256 双端对比 | ✅ 更强 |
| 4-5. tar 保留/rm+mkdir | tar 流程 | Full 保留；Fast 无 tar | ✅ N/A |
| 6. Nginx 代理指向正确 | `docker exec grep proxy_pass` | 保留 | ✅ 一致 |
| 7. 端到端验证 | 手工 curl 5 项 | 自动 `verify_apis.py` + browser-use 全链路 | ✅ 更强 |
| 8. Docker 缓存清理 | `builder prune -af` | 仅在 Full 或 pom/package.json 变化时清理；Fast 保留 layer cache | ⚠️ 需新决策 D-12 补充 |

**新决策 D-12（本方案携带）**：Fast 档保留 Docker 构建缓存，因为源码变化通过 jar/dist 产物级替换保证一致性，与铁律 2/8 的"防止代码回退"目标不冲突。

## 五、每次部署完成后的自动验证（铁律 7 强化）

1. **API 冒烟**：curl 走前端端口跑 Layer 2 §16 五步清单 → 输出 `verify_apis.json`。
2. **Playwright 冒烟**（无 LLM 版本，稳定）：
   - admin 登录
   - 主菜单遍历（PC 26 个模块）
   - 移动端 H5 登录 + 5 个高频页面
   - 关键写操作（新建/删除产品、订单）
3. **browser-use Agent 探索**（有 LLM 时启用）：跑用户故事 US-A/B/C/D 场景。
4. **失败处理**：任何一项失败 → 自动回滚容器到上一个 rollback tag + 输出诊断报告到 `docs/09_测试报告/autotest/`。
