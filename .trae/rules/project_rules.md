# DMS 项目规则

## 核心规则（必须遵守）

### 1. 📝 文档更新规则
每次完成功能开发/需求整改后，**必须更新现有文档**，遵循以下规则：
- 更新位置：`docs/02_需求分析/需求分析_UserStory.md` - 在版本变更速览和附录中新增迭代记录
- 更新位置：`docs/04_功能详细设计/功能详细设计.md` - 在变更日志开头新增版本变更说明
- 更新位置：`docs/05_数据库设计/数据库设计.md` - 在开头新增数据库变更说明
- 更新位置：`docs/09_测试报告/测试报告.md` - 新增完整章节，逐项记录需求、实现、测试场景、结论
- 更新根目录 `README.md` - 版本号、交付要点、测试成绩更新到最新
- **禁止新建文档**，只在现有文档上追加迭代内容
- 版本号递增：v3.5.x → 下一个小版本号，日期更新为当天

### 2. ✅ 交付自查规则（交付前必须按此清单逐项检查通过）
**交付前必须按照《交付自查清单》逐项检查，全部通过才能交付**。

必须检查：
- 所有服务能正常启动（PostgreSQL/Redis/Backend/Frontend）
- 能正常登录（admin账号密码正确）
- 本次修改的所有需求逐项验证通过
- 没有回归破坏原有功能
- 文档全部更新完成
- 项目文件夹清理完成（无过时冗余文件）

### 3. 🚀 部署执行规则
**AI 自动部署，无需用户催促**：代码修改完成后，AI 必须主动、立即部署到测试环境，不需要用户多次询问"为什么还没部署"。
- 部署流程：代码完成 → 提交 git → 连接服务器 → 拉取代码 → 构建部署 → 验证功能
- 发现配置问题修复后，AI 直接执行部署，不需要等用户说"帮我部署"才行动
- 用户只需要等待结果并反馈验证情况

### 3.2 📦 JAR直投部署规则（推荐，高效）
采用 JAR 直投模式替代服务器端 Maven 编译，发布时间从 30-60 分钟压缩到 5 分钟以内：

1. **部署流程**：
   - 在本地/CI 或服务器临时容器中执行 `mvn clean package -DskipTests` 打包
   - 生成 `backend/target/dms-backend.jar`
   - 使用 `Dockerfile.runtime` 构建镜像（只复制 JAR，不编译）
   - 重启服务完成部署

2. **Dockerfile.runtime 内容**（已存在）：
   ```dockerfile
   FROM eclipse-temurin:17-jre-alpine
   WORKDIR /app
   RUN apk add --no-cache curl tzdata \
       && cp /usr/share/zoneinfo/Asia/Shanghai /etc/localtime \
       && echo "Asia/Shanghai" > /etc/timezone
   COPY target/*.jar app.jar
   ENV JAVA_OPTS="-Xms256m -Xmx1024m -Duser.timezone=Asia/Shanghai"
   EXPOSE 8080
   ENTRYPOINT ["sh","-c","java $JAVA_OPTS -jar app.jar"]
   ```

3. **本地无法打包时的备选方案**：
   - 在服务器上使用临时 Maven 容器打包
   - 命令：`docker run --rm -v $(pwd):/build -w /build maven:3.9-eclipse-temurin-17 mvn clean package -DskipTests`

### 3.1 🌍 双环境管理规则（测试环境 → 正式环境）

#### 环境说明
| 环境 | 地址 | 用途 | 数据库 |
|------|------|------|--------|
| 测试环境 | `http://8.133.193.238:8083` | 需求开发、功能调整、验证测试 | dms_test |
| 正式环境 | `http://8.133.193.238:8081` | 生产演示、正式使用 | dms |

#### 核心规则（必须严格遵守）
1. **所有需求调整和功能修改，只能先部署到测试环境验证**，禁止直接修改正式环境
2. 测试环境验证完成后，**必须等待用户明确说"推送正式环境"或类似确认指令**，才能更新正式环境
3. 推送正式环境前，AI 必须主动向用户确认本次变更内容，用户确认无误后再执行
4. 正式环境只允许做以下操作：
   - 用户明确确认后的版本推送
   - 紧急问题修复（需用户明确授权）
5. 代码修改统一先更新到测试环境，验证通过后再复制到正式环境

#### 推送正式环境流程
1. AI 测试环境验证功能正常
2. AI 向用户汇报变更内容和测试结果
3. 用户说"推送正式环境"
4. AI 执行正式环境更新（代码/镜像/数据库迁移等）
5. AI 验证正式环境可用后通知用户

### 4. 🧹 项目清理规则
- 删除过时重复目录（如旧前端版本、验证分支）
- 删除临时调试脚本（根目录大量 *.py 调试文件用完即删）
- 删除旧压缩备份文件（*.tar.gz）
- 删除重复 README（只保留根目录一个入口）
- 保持项目结构干净整洁

### 5. 🧑‍💻 代码风格规则
- 不添加注释，除非用户明确要求
- 遵循现有代码的命名和风格约定
- 优先编辑现有文件，不轻易新建文件

### 6. 🗄️ 数据库迁移规则
- 使用 Flyway 版本管理，文件名格式 `V{version}__{description}.sql`
- 版本号连续递增，不重复不跳过
- 只做增量变更，不修改已执行的迁移文件

### 7. 🎨 前端配置规则
- 模块配置在 `frontend-vue/src/config/modules.js`
- 菜单配置在 `frontend-vue/src/config/menu.js`
- 遵循已有的 `form` 字段和 `cols` 配置格式

### 8. 📋 需求处理流程（每次收到需求调整都必须遵守）
1. **先理解，后动手**：收到需求后先完整理解意图，**不得擅自开始编码或修改**。
2. **有疑必问**：任何不清楚、有歧义或存在多种实现方案的地方，**必须先与用户确认**，确认完全正确后再继续，禁止凭假设推进。
3. **逐条不遗漏**：仔细通读用户给出的**所有**修改意见，逐条落实，一条都不能漏；建议用清单（TodoWrite）逐项跟踪。
4. **完成后复检**：全部完成后再对照原始需求**整体检查一遍**，确认每条意见都已实现且无副作用，再向用户汇报。
